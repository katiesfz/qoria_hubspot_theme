# Wiki maintainer

The wiki is a **developer** reference for this repo. It lives in a separate git
repo cloned at `../Q_Theme.wiki` (relative to the repo root), which is listed in
`.claude/settings.json` as an additional directory. Editors (marketing, sales,
success) are served by the Notion guide, not here, so don't write how-to-use-in-the-editor
content.

## Rules

1. **Write files only. Never commit or push** either repo. When you finish, say what
   changed and tell the user to review and push from `Q_Theme.wiki` themselves.
2. **Document what the code does, not what you guess.** Read the file before describing
   it. If something is unclear or looks wrong, put it in an "Open questions" list in
   your reply rather than into the page.
3. **Never change anything in HubSpot** (`hs upload`, `hs watch`, etc.). Reading the repo is all you need.
4. **No secrets.** Don't copy tokens, personal access keys or `hubspot.config.yml`
   contents into the wiki. Secret *names* (e.g. `HUBSPOT_PAK_UK`) are fine.
5. **Wiki links use page names, not paths:** `[text](Page-Name)`, no `.md`. Page files are
   `Title-Case-With-Hyphens.md`. Link to code with repo-relative paths in backticks.
6. **Docs live in the wiki, not in `docs/`.** Feature docs were moved here from the
   repo's `docs/` folder. Don't recreate them in `docs/`. (`docs/old/` is a legacy
   page-designer guide and is out of scope.)
7. **Don't edit generated pages by hand.** Pages starting with the
   `<!-- generated by wiki-maintainer/... -->` marker are overwritten on every run.

Add a new `Feature` page (same style as the existing four: what it does, where it lives,
how to configure, things to know) whenever the user asks to document a feature that
isn't covered, and add it to `_Sidebar`.

## Build (first run, or "rebuild the wiki")

1. Confirm `../Q_Theme.wiki` exists and `git -C ../Q_Theme.wiki pull` is clean. If not, stop and tell the user.
2. Generate the module pages:
   `python .claude/skills/wiki-maintainer/scripts/module_reference.py . ../Q_Theme.wiki`
   Use `--dry-run` first if pages already exist. The script skips any page that lacks the generated marker and removes pages for deleted modules.
3. Write each hand-written page in the table, reading its sources first. Keep pages short and
   scannable: a one-paragraph purpose, then tables or lists. Skip a page rather than pad it
   when the source has nothing real to say yet.
4. Write `Home` (purpose, audience, one line + link per page) and `_Sidebar` (grouped links:
   Start, Architecture, Reference, Features, Migration). In `_Sidebar` list `Modules` only,
   not the 178 module pages.
5. Write `_Footer`: `Synced with Q_Theme commit <short sha> on <date>.`
   (`git rev-parse --short HEAD`). Note in your reply if the repo had uncommitted changes.

## Maintain (later runs, "update the wiki")

1. Read the sha from `../Q_Theme.wiki/_Footer.md`. List what changed:
   `git diff --name-only <sha>` plus `git status --porcelain` for uncommitted and untracked files.
2. Map changed paths to pages with the table above:
   - `hubspot/*/modules/**` → re-run `module_reference.py`; also update a Feature page if one covers that module.
   - `hubspot/*/sections/**`, `hubspot/*/templates/**` → `Sections-and-Templates`.
   - `package.json`, `vite.config.js`, `.github/workflows/*.yaml`, `scripts/**` → `Build-and-Deploy` (and `Getting-Started` if setup changed).
   - `migration/STATUS.md` → `Migration`.
   - `figma/tokens.json`, `css/` variables → `Design-Tokens`.
   Ignore changes that don't affect documented behaviour (formatting, `.bak`, minified output).
3. Update only the affected pages, in place. Don't rewrite pages whose sources didn't change.
4. Update the sha and date in `_Footer`, and `_Sidebar` if pages were added or removed.

## Finish

Run `git -C ../Q_Theme.wiki status --short` and reply with: pages created, pages updated,
pages skipped and why, and any open questions. Then remind the user to review and push
from `Q_Theme.wiki`.
